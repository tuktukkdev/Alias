### 1.1 Постановка задачи и требования к системе

#### Обоснование необходимости разработки

Настольная игра «Alias» — одна из наиболее популярных словесных игр, в которой участники объясняют слова без использования однокоренных форм. Классическая версия игры ограничена физическим присутствием участников и комплектом карточек, что существенно сужает аудиторию и возможности.

Разработка веб-версии решает следующие проблемы:

- **Географическая ограниченность** — игроки не могут играть вместе, находясь в разных городах или странах;
- **Ограниченный набор слов** — физический набор содержит фиксированное количество карточек, слова быстро запоминаются;
- **Отсутствие персонализации** — нет возможности добавить слова на специфическую тематику;
- **Нет учёта статистики** — результаты игр нигде не фиксируются и не накапливаются.

Выгоды для пользователей:
- Возможность играть онлайн с друзьями из любой точки мира;
- Создание собственных тематических коллекций слов;
- Голосовая связь внутри игровой комнаты;
- Личная статистика (угаданные/пропущенные слова, победы/поражения);
- Система друзей для поиска знакомых игроков.

#### Описание предметной области

**Основные участники:**
- **Игрок** —  пользователь, участвующий в игровых сессиях;
- **Хост** — игрок, создавший комнату; управляет её настройками и запускает игру;
- **Гость** — игрок, присоединившийся к чужой комнате по коду или ссылке.

**Основные сущности:**
- **Комната** — игровая сессия с уникальным идентификатором, настройками (таймер, победный счёт, сложность, выбор коллекций) и списком игроков;
- **Коллекция слов** — именованный набор карточек; бывает стандартной (системной) или пользовательской;
- **Карточка** — слово с уровнем сложности (1–3);
- **Игровой раунд** — ход одного игрока, в течение которого он объясняет слова, а остальные угадывают в чате.

**Бизнес-правила:**
- Комнату может создать только авторизованный или гостевой пользователь (имя обязательно);
- Игру может начать только хост, и только при наличии минимум двух подключённых игроков;
- За угаданное слово начисляется +1 очко активному и угадавшему игроку; за пропуск снимается −1;
- Победа фиксируется при достижении настроенных`winScore` очков; статистика обновляется в БД;
- Каждый пользователь может одновременно находиться только в одной комнате;
- Email верификация не является обязательным условием для игры, но рекомендуется, для избежания потери аккаунта.

#### Характеристика процессов функционирования

**Сценарий 1: Регистрация и вход**
1. Пользователь заполняет форму (username, email, пароль) → сервер валидирует → создаёт запись в БД → отправляет письмо верификации;
2. Пользователь входит по username + пароль → сервер проверяет хэш → возвращает данные сессии.

**Сценарий 2: Создание и проведение игры**
1. Хост создаёт комнату: `POST /rooms` → сервер генерирует ID → возвращает состояние комнаты;
2. Хост делится кодом/ссылкой с игроками;
3. Каждый игрок подключается через WebSocket (`/ws?roomId=...&playerId=...`);
4. Хост нажимает «Начать» → `POST /rooms/:id/start` → сервер запрашивает согласие(наличие в комнате) всех → при подключении всех запускает отсчёт;
5. Сервер генерирует слово (`wordService.pickWordFromPool`) → рассылает активному игроку через WebSocket;
6. Остальные угадывают в чате → при совпадении слово засчитывается;
7. Таймер истекает и слова угаданы или пропущены → ход передаётся следующему игроку;
8. Первый достигший `winScore` объявляется победителем → сервер сохраняет результат в БД.

**Сценарий 3: Голосовой чат**
1. При входе в комнату клиент запрашивает доступ к микрофону;
2. Через WebSocket обмениваются WebRTC offer/answer/ICE-кандидатами;
3. После установки P2P-соединения аудио передаётся напрямую между игроками.

**Сценарий 4: Управление коллекциями**
1. Пользователь создаёт коллекцию → добавляет слова → сохраняет;
2. При создании комнаты хост выбирает нужные коллекции;
3. Сервер загружает слова из выбранных коллекций в пул; дефолтные — через Redis-кэш, пользовательские — напрямую из БД.

### 1.2 Проектирование информационной системы

#### Выбор архитектурных решений

Для системы выбрана **клиент-серверная архитектура** со следующим обоснованием:

- **Монолит против микросервисов**: на данном этапе объём функциональности не требует разбиения на независимые сервисы. Монолитный бэкенд проще в развёртывании, отладке и сопровождении. При необходимости масштабирования отдельные модули (например, голосовой сигналинг) могут быть вынесены в отдельные сервисы.
- **Stateful WebSocket на стороне сервера**: игровое состояние хранится в оперативной памяти сервера (`Map`-структуры), что обеспечивает минимальную задержку при синхронизации. Redis используется для кэширования слов, а не для игрового состояния.
- **SPA (Single Page Application) на клиенте**: весь UI управляется React без перезагрузок страниц, что критично для real-time игры.
- **Nginx как reverse proxy**: в production nginx обслуживает статику клиента и проксирует API-запросы к Node.js-серверу, обеспечивая SSL-терминацию.

└──────────────────────────────────────────────────────────┘
                          │
                    ┌─────▼──────┐

                    └─────┬──────┘
                          │
               ┌──────────▼─────────────┐
               │   Node.js / Express    │
               │  ┌─────────────────┐   │
               │  │  REST Routes    │   │
               │  │  WS Server      │   │
               │  │  Services       │   │

               └───────────┼────────────┘
                    ┌───────┴──────┐
            ┌───────▼──────┐  ┌───▼────┐

#### Структура программного проекта

#### Описание реализованных модулей

**`authService.ts` — аутентификация и управление пользователями**

Реализует: регистрацию (`registerUser`), вход (`loginUser`), смену username/пароля, аватар, статистику, email-токены для верификации и сброса пароля.

Ключевые функции:
- `hashPassword(password)` — генерирует случайную соль (16 байт), вычисляет ключ через `scrypt(password, salt, 64)`, возвращает строку `"salt:key"`;
- `verifyPassword(password, stored)` — разбирает хэш, вычисляет производный ключ, сравнивает через `timingSafeEqual` (защита от timing-атак);
- `registerUser(username, email, password)` — проверяет уникальность, хэширует пароль, создаёт пользователя и пустую запись статистики;
- `createEmailVerificationToken(userId)` — генерирует 32-байтный токен (64 hex-символа), сохраняет в `email_tokens` с типом `verify` и TTL 24 ч.

**`roomService.ts` — игровая логика**

Реализует создание/закрытие комнат, запуск игры, игровой тик, передачу хода, победу, запись результата в БД.

Ключевые функции:
- `getNextTurnPlayerId(players, currentTurnPlayerId)` — кольцевой переход хода; при достижении последнего игрока возвращает первого;
- `buildRoomStatePayload(roomId, record)` — формирует снимок состояния комнаты для отправки через WebSocket;
- `allPlayersConnected(record)` — проверяет, все ли игроки в `connectedPlayerIds`;
- `startRoomGame(roomId, record, broadcasters)` — загружает пул слов, запускает обратный отсчёт (3 с), затем запускает тик-интервал;
- `startRoomTickLoop(roomId, record, broadcasters)` — каждую секунду декрементирует таймер; по истечении — разрешает слово, передаёт ход.

**`wordService.ts` — пул слов**

- `loadWordPool(record)` — собирает слова из пользовательских коллекций (БД) и дефолтных (Redis-кэш), с фолбэком на слова по сложности и на все слова;
- `pickWordFromPool(record)` — выбирает случайное неиспользованное слово; при исчерпании сбрасывает `usedWords` и начинает заново; при пустом пуле возвращает строку `'слово'`.

**`cacheService.ts` — Redis-кэш**

- `preloadDefaultCollections()` — при старте сервера загружает все дефолтные коллекции в Redis (ключи `col:default:{id}`, `col:general:{diff}`, `col:general:all`);
- `getDefaultCollectionWordsCached(id)` — читает из Redis; при промахе делает запрос в PostgreSQL.

**`socketServer.ts` — WebSocket**

- Парсит `roomId` и `playerId` из query-параметров подключения;
- При подключении отменяет таймеры офлайна, рассылает актуальное состояние;
- Поддерживает соединение ping-интервалом (30 с) для обхода таймаутов Cloudflare;
- При отключении запускает таймер кика (если только один сокет этого игрока);
- Маршрутизирует входящие события: чат, голосовые сигналы (WebRTC offer/answer/ICE).

**`App.tsx` — корневой клиентский компонент**

Управляет навигацией между экранами (`page` state), жизненным циклом WebSocket-соединения, состоянием комнаты, восстановлением сессии из `localStorage`. При получении WS-событий обновляет `roomState`, `chatMessages`, `activeWord`, `gameStartsIn`.

**Голосовой чат (`useVoiceChat`):**

WebRTC-соединения устанавливаются через сигналинговый канал WebSocket. Для каждого участника создаётся отдельный `RTCPeerConnection`. Микрофон захватывается с параметрами шумоподавления и эхоподавления (`echoCancellation: true, noiseSuppression: true`). Целевой битрейт Opus-кодека — 48 кбит/с. Активный говорящий (текущий ход) визуально выделяется в интерфейсе.

#### Описание ключевых алгоритмов

**1. Хэширование паролей (scrypt)**

```
hashPassword(password):
  salt ← randomBytes(16).hex
  key  ← scrypt(password, salt, keylen=64)
  return salt + ":" + key.hex

verifyPassword(password, stored):
  [salt, hash] ← stored.split(":")
  if not salt or not hash: return false
  key ← scrypt(password, salt, keylen=64)
  storedKey ← Buffer.fromHex(hash)
  if key.length ≠ storedKey.length: return false
  return timingSafeEqual(key, storedKey)
```

Функция `timingSafeEqual` выполняет сравнение за постоянное время независимо от содержимого буферов, что предотвращает атаки по времени (timing attack).

**2. Выбор случайного слова из пула**

```
pickWordFromPool(record):
  pool ← record.wordPool
  if pool is empty: return "слово"
  
  available ← pool.filter(w → w ∉ record.usedWords)
  if available is empty:
    record.usedWords.clear()
    return pool[random(pool.length)]
  
  return available[random(available.length)]
```

Сложность: O(n) по размеру пула. Алгоритм гарантирует отсутствие повторений до полного обхода всего пула.

**3. Кольцевая передача хода**

```
getNextTurnPlayerId(players, currentId):
  if players.length = 0: return null
  idx ← players.findIndex(p → p.id = currentId)
  if idx = -1: return players[0].id
  return players[(idx + 1) mod players.length].id
```

Сложность: O(n). Обеспечивает справедливое чередование ходов без дискриминации последнего игрока.

**4. Игровой тик (таймер)**

```
startRoomTickLoop(roomId, record, broadcasters):
  interval ← setInterval(1000ms):
    if record.turnSecondsRemaining > 0:
      record.turnSecondsRemaining -= 1
      broadcast(roomState)
    else:
      if record.waitingForWordResolutionAtZero:
        resolveCurrentWord(skip=true)
      else:
        record.waitingForWordResolutionAtZero ← true
        broadcast(roomState)
```

При достижении нуля сервер ждёт финального ответа или принудительно пропускает слово, избегая гонки условий (race condition) между истечением таймера и угадыванием.

## 8. Найденные дефекты и их устранение

| ID | Дефект | Серьёзность | Причина | Исправление |
|---|---|---|---|---|
| BUG-01 | Хранимый хэш некорректного формата (без `:`) вызывал `timingSafeEqual` с разными длинами буферов | Средняя | Не проверялся формат хэша | Добавлена проверка `if (!salt \|\| !hash) return false` в `verifyPassword` |
| BUG-02 | `app.options("*", ...)` падал с ошибкой в Express 5 из-за path-to-regexp | Высокая | Несовместимость синтаксиса | Заменено на `app.options(/.*/, ...)` |
| BUG-03 | При пустом `wordPool` (`null`) вызов `filter` приводил к TypeError | Низкая | `wordPool` может быть `null` до `loadWordPool` | Добавлена проверка `if (pool && pool.length > 0)` |
| BUG-04 | Параметры маршрута `:roomId` могли иметь тип `string \| string[]` | Низкая | Типы Express v5 | Добавлена нормализация `String(req.params.roomId)` |
| BUG-05 | Нагрузочный тест `room-load.js` выполнял 480 901 итерацию с `error_rate=100%` при незапущенном сервере — все запросы мгновенно завершались ошибкой `connection refused`, счётчики раздувались | Высокая | Отсутствие предварительной проверки доступности сервера | Добавлена функция `setup()` в оба load-скрипта: если сервер недоступен, тест прерывается с понятным сообщением ещё до фазы нагрузки |

### 9.2 Установка k6 (нагрузочные тесты)

k6 — отдельный бинарный инструмент, не устанавливается через npm.

**Windows (через winget):**
```bash
winget install k6 --source winget
```

**Windows (через Chocolatey):**
```bash
choco install k6
```

**macOS:**
```bash
brew install k6
```

**Linux (Debian/Ubuntu):**
```bash
sudo gpg -k
sudo gpg --no-default-keyring --keyring /usr/share/keyrings/k6-archive-keyring.gpg \
  --keyserver hkp://keyserver.ubuntu.com:80 --recv-keys C5AD17C747E3415A3642D57D77C6C491D6AC1D69
echo "deb [signed-by=/usr/share/keyrings/k6-archive-keyring.gpg] https://dl.k6.io/deb stable main" \
  | sudo tee /etc/apt/sources.list.d/k6.list
sudo apt-get update && sudo apt-get install k6
```

Проверка установки:
```bash
k6 version
```

Подробнее: https://k6.io/docs/get-started/installation/
